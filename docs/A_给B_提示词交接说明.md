# A 给 B：Prompt 与输出字段交接说明

> 用途：向 B 说明 A 期望的 Prompt 交付物与模型输出字段契约，保证后续统计能对齐。
> 背景：项目是「同一模型 × 三版 Prompt」对受控代码样本的判断评估，A 负责判定标准、真值与统计。

## 一、B 的交付物

SQLi 与 XSS 各 V0 / V1 / V2，共 6 份完整 Prompt 文本，存 `prompts/`（现有 V0 为候选草稿，需真实迭代）。

## 二、模型输出字段契约（A 用于映射到 runs/formal.json）

Prompt 应要求模型对每个样本返回结构化结论，至少含：

1. **判定结论**：`vulnerable` / `safe` / `uncertain` 三选一（与 `docs/metrics_protocol.md` 一致；
   `uncertain` 表示模型明确需要补充信息，不是「没找到」）。
2. **定位**：目标缺陷所在的文件与行号（输入包内为中性别名 `F01:0017` 形式）。
   定位正确与判定正确分开计，A 会单独核 `location_correct`。
3. **验证脚本（POC）**：给出可运行脚本，或明确写「未生成」。未生成不得由执行人补一份冒充模型输出。
4. **依据**：引用到的代码位置与判断理由（A 据此核对「预测正确但位置编造」的情况）。

## 三、对齐的判定与口径

- 判定标准：`docs/judgment_criteria.md`（SQLi 四项检查、XSS 五项检查、满足/不满足/未知）。
- 统计口径：`docs/metrics_protocol.md`（TP/FP/TN/FN/U_positive/U_negative、精确率、保守召回率、
  误报率、待判定率、POC 可执行 vs 漏洞触发分离）。

## 四、中立性与隔离要求

- Prompt 不得泄露样本标签/答案；`sample_card.md`、`truth_review.md`、`line_map.json` 等内部文件不发给模型。
- B 设计 Prompt 时不读取正式测试样本（S007/S008/S019/S024 等）的真值答案。
- 样本输入是 C 用 `tools/prepare_input.py` 生成的 `code_input.txt`（`F01`/`F02` 中性别名 + 行号），不含内部注释。

## 五、三版差异建议（供参考，不强制）

- V0：直接请求判断与定位。
- V1：强化定位与逐条依据（对应判定卡检查项）。
- V2：增加验证脚本要求与可执行性说明。
- 迭代发生在开发集（SQL01–SQL03、XSS01–XSS03）；正式测试开始后冻结 Prompt，不再回改。

## 六、需要 B 回传的

- 6 份 Prompt 全文 + 每版的哈希（冻结单用）。
- 每个开发样本的首轮原始输出与迭代问题单（供 A 核对字段是否齐全、是否泄露答案）。
