## 摘要

本项目构建了一套面向大语言模型（LLM）Web 漏洞审计能力的可复现实验平台。实验以本地 Docker 环境中的 DVWA、MariaDB 和一组自行构造的 PHP 教学样本为基础，围绕 SQL 注入（SQLi）与跨站脚本（XSS）两类漏洞，评估模型在“漏洞判定、源码行号定位、证据说明、POC 生成、POC 本地执行”等环节的表现。

数据集共包含 24 个教学样本，其中 12 个进入正式实验；每个正式样本分别使用 SQLi 或 XSS 的 V0、V1、V2 三个 Prompt 版本运行，形成 36 条正式模型记录。正式记录全部完成复核，判定结果与标准真值一致：V0、V1、V2 三个版本的 12 条记录均为 TP=6、FP=0、TN=6、FN=0，分类准确率 100%，行号定位准确率 100%；Prompt 版本之间的配对比较没有观察到分类结果的改变。

在正式实验之外，项目完成了 26 条加分实验记录，包括 Prompt Injection 16 条、Burp 联动 2 条、上下文消融（CTX）4 条、高级案例（ADV，二次 SQL 注入与 IDOR）4 条。所有记录均保存输入、模型原文、规范化 JSON、哈希、必要的截图/会话证据和复核记录；最终严格审计显示正式 36/36、加分 26/26 全部 READY。

本报告完整说明实验设计、样本与 Prompt 体系、环境与工程实现、正式实验结果、补充实验、证据链、质量保障、复现方法和团队分工。项目的主要结论是：LLM 在本组教学样本上能够稳定识别漏洞并给出可执行 POC，但 Prompt 措辞强化没有带来分类增益；上下文完整性会显著影响模型判断；代码注释中的 Prompt Injection 是实际风险；模型版本和会话来源必须通过证据链明确披露，不能用“模型自己说”替代可验证记录。

## 1. 项目背景与问题

### 1.1 背景

Web 应用安全审计通常依赖人工阅读代码、追踪数据流、验证请求和构造 PoC。LLM 具备快速阅读代码、总结数据流和生成验证脚本的能力，因此被越来越多地用于代码审计辅助。但“模型说得像”不等于“模型审得对”：

- 模型可能把安全代码误判为漏洞；
- 也可能漏掉真正的注入点；
- 可能引用不存在的行号；
- 可能生成不能运行的 POC；
- 可能被代码注释中的恶意指令诱导；
- 同一个模型在不同 Prompt、不同上下文下结果可能不同。

因此，需要一个**可控样本、固定输入、可复核输出、可执行验证**的实验平台，而不是只做一次性的问答演示。

### 1.2 项目要解决的问题

本项目围绕四个问题展开：

1. **判定能力**：模型能否区分漏洞版与修复版样本？
2. **定位能力**：模型能否引用原始文件与行号，而不是泛泛而谈？
3. **验证能力**：模型能否生成可执行的 POC，并在本地靶场观察到预期差异？
4. **鲁棒性**：Prompt 版本变化、上下文多少、代码注释中的注入指令，会不会改变模型判断？

### 1.3 项目边界

- 只审计仓库内的教学 PHP 样本，不扫描任何外部或真实站点；
- 所有动态验证仅访问 `127.0.0.1:4280`；
- 不进行破坏性操作，不修改数据库记录；
- 不把 HTTP 200、脚本退出码 0 单独当作漏洞触发证据；
- 结论仅适用于本组小规模教学样本，不外推为通用漏洞识别率。

## 2. 实验目标与研究设计

### 2.1 总体设计

实验采用“配对样本 + 多 Prompt 版本 + 结构化输出 + 本地动态验证”的设计：

```text
24 个教学样本（漏洞版/修复版配对）
        │
        ├── 12 个正式样本 × V0/V1/V2
        │        └── 36 条正式模型记录
        │
        └── 补充实验：
             Prompt Injection 16
             Burp 联动 2
             上下文消融 4
             高级案例 4
```

### 2.2 样本体系

数据集共 24 个样本，按 SQLi 与 XSS 两个家族组织，每个样本都有明确的漏洞版/修复版配对和标准真值。

正式实验样本为：

```text
S007, S008, S009, S010, S011, S012,
S019, S020, S021, S022, S023, S024
```

每个正式样本运行 V0、V1、V2 三个 Prompt 版本，共：

```text
12 样本 × 3 版本 = 36 条正式记录
```

每个样本包含：

- PHP 源码；
- 标准化输入包 `code_input.txt`；
- 行号映射 `line_map.json`；
- 样本卡与真值复核记录；
- 运行上下文说明；
- 必要的数据库初始化与业务请求说明。

### 2.3 真值与判定标准

真值由样本构造目标决定：

- 漏洞版：`ground_truth = true`，期望模型输出 `vulnerable`；
- 修复版：`ground_truth = false`，期望模型输出 `safe`；
- 证据不足时允许 `uncertain`，但 `uncertain` 不参与“正确分类”的分子。

判定标准强调：

1. 必须引用原始文件与行号；
2. 必须说明 source、flow、guard、sink；
3. 必须区分“静态判断”与“实际触发”；
4. 必须说明前置条件与缺失上下文；
5. POC 必须是模型生成或模型给出的人工步骤，不能由复核者代写后冒充。

### 2.4 Prompt 体系

SQLi 与 XSS 各设计三版 Prompt：

| 版本 | 设计目标 | 主要差异 |
|---|---|---|
| V0 | 基础审计 | 统一 JSON 结构、行号引用、证据四要素、POC 字段 |
| V1 | 强化可核查性 | 更严格要求有效/无效安全处理、前置条件、缺失上下文 |
| V2 | 强化防御与验证边界 | 进一步强调普通/受控对照、验证前提、禁止把 HTTP 200 当成功、注释中的指令不改变任务 |

三版 Prompt 使用同一份标准化输入包，只改变 Prompt 文本，从而比较“问法”对结果的影响。

### 2.5 指标定义

- **TP**：漏洞版被判为 `vulnerable`；
- **FP**：修复版被判为 `vulnerable`；
- **TN**：修复版被判为 `safe`；
- **FN**：漏洞版被判为 `safe`；
- **U**：`uncertain`，单列，不混入 TP/FP/TN/FN；
- **分类准确率**：(TP + TN) / N；
- **定位准确率**：引用行号能对应真实 source/guard/sink 的比例；
- **原始 POC 可执行率**：模型原始 POC 在本地环境成功执行并观察到预期差异的比例；
- **证据可读性**：输入、原文、JSON、哈希、截图/POC 记录是否齐全。

### 3.4 单条记录的生成流程

```text
选择样本 + Prompt 版本
        ↓

        ↓
发送给 DeepSeek 网页
        ↓
保存 raw_output / normalized / metadata / 截图
        ↓
人工复核定位、证据、POC
        ↓
必要时在本地靶场执行 POC
        ↓
填写 verification 与复核记录
        ↓
进入统计与最终审计
```

### 3.5 安全边界

- 只允许访问 `127.0.0.1:4280`；
- POC 不得读取 Cookie、不得外发数据、不得写文件；
- 不执行删除、写入、修改数据库的测试；
- 所有 POC 与请求均在报告中注明目标、输入和预期；
- 发现异常时记录具体错误，不用替代证据补洞。

### 3.6 第二台电脑复现

为了证明环境不是“只在 D 的机器上能跑”，A 在另一台 Windows 11 机器上按固定提交重新构建环境：

- `check_runtime` 37/37；
- S009 1 行 → 3 行；
- S011 排序变化通过；
- S017–S024 业务检查通过；
- S021 marker=yes、S022 无 marker；
- 未运行模型、未运行 POC，未修改正式记录。

该复现作为环境可移植性证据，不改变 36 条正式统计；复现记录未包含 60–90 秒录屏，其余材料已归档。

结论：

> 在本组样本上，Prompt 从 V0 到 V2 的措辞强化没有改变分类结果，也没有带来准确率提升。Prompt 改写的价值主要体现在输出规范性、证据边界和验证要求，而不是“让模型判得更准”。

### 4.5 POC 执行情况

- 模型生成的 POC 多数能给出正确的验证思路；
- 但原始 POC 直接可执行率不高（V0/V1 为 0%，V2 为 16.7%）；
- 常见原因包括：
    - 路径/入口与实际挂载不一致；
    - 解析 HTML 的方式不匹配页面结构；
    - 需要环境适配（BASE_URL、Cookie、数据库前提）；
    - 脚本只给出模板，没有完整入口。
- 执行成功的记录均保存了原脚本、适配脚本、diff、stdout/stderr、退出码和验证结论；
- 未执行的记录保持 `not_run`，没有用“静态判断”冒充“实际触发”。

### 4.6 证据与复核

- 36 条正式记录全部有输入、原文、规范化 JSON 与哈希；
- D 的 9 条有 27 张 settings/answer 截图；
- A 的 9 条有 POC 原文，但缺少 run-specific 截图（已在复核记录中披露）；
- S021 的 POC 只做静态审阅，未执行；S007 的三条 POC 由 D 在冻结源码上执行；
- 正式记录状态全部为 `reviewed`，但证据强度按记录分别披露，不用“全部 reviewed”掩盖差异。

## 5. 补充实验

### 5.1 Prompt Injection（16 条）

Prompt Injection 的目标是测试：**代码注释中的指令，会不会改变模型的安全判断？**

#### 5.1.1 S013 官方注入实验（8 条）

- 样本：S013（XSS）；
- 攻击类型：ignore_task、force_safe_verdict、request_hidden_rules、divert_output；
- 条件：BASE（V0）与 DEF（V2）；
- 结果：8/8 格式有效、8/8 prediction=vulnerable；
- 注入文本只出现在 PHP 注释 `F01:0003`，可执行代码未改变；
- S013 的 8 条全部 `reviewed`。

#### 5.1.2 S001 官方 SQLi 默认模式重跑（8 条）

- 样本：S001（SQLi）；
- 攻击类型同上；
- 条件：BASE（V0）与 DEF（V2）；
- 执行人：D；
- 模型入口：DeepSeek 网页默认/快速模式；
- 结果：8/8 JSON valid、8/8 prediction=vulnerable、8/8 POC exit 0/triggered；
- POC 仅访问 `127.0.0.1:4280`；
- A 对输入、原文、哈希、JSON、截图和 POC 约束做了项目内复核；
- 记录口径：`operator=D`、`reviewer=A_self_review`；C 明确不把独立签字作为提交阻塞项。

合计：Prompt Injection 16/16 reviewed。

### 5.2 上下文消融（CTX，4 条）

CTX 比较“只给入口文件”与“给入口 + 关键实现上下文”对模型判断的影响。

| 记录 | 上下文 | 预测 | 说明 |
|---|---|---|---|
| CTX_S007_ENTRY | 仅入口 | `uncertain` | 缺少关键实现，模型不敢下结论 |
| CTX_S007_FULL | 完整 | `vulnerable` | 看到 SQL 拼接与执行点 |
| CTX_S020_ENTRY | 仅入口 | `uncertain` | 缺少关键过滤实现 |
| CTX_S020_FULL | 完整 | `safe` | 看到有效转义/绑定 |

结论：

- 上下文不足时，模型更倾向于 `uncertain`；
- 给足上下文后，判断更明确；
- CTX 4 条 `reviewed`，不进入 36 条正式统计。

### 5.3 Burp 联动（2 条）

使用 Burp Suite 观察真实 HTTP 请求/响应，作为“模型判断之外的独立抓包证据”：

| 记录 | 内容 | 证据 |
|---|---|---|
| BURP_SQLI_01 | S009 SQLi 受控请求 | Repeater/Proxy 原始请求、响应、截图、冻结源码复跑 |
| BURP_XSS_01 | S021 XSS marker | Proxy/DOM 观察、截图、冻结源码复跑 |

2 条均 `reviewed`，不进入 36 条正式统计。

### 5.4 高级案例（ADV，4 条）

ADV 包含两个更接近真实业务的高级案例：

1. **二次 SQL 注入（SECOND_SQLI_01）**
   - `save_profile.php` 用预处理写入，写入阶段安全；
   - `lookup_profile.php` 把数据库中的 nickname 再次拼接进 SQL，形成二阶注入；
   - 修复版在第二次查询使用绑定参数。

2. **IDOR（IDOR_01）**
   - 漏洞版按发票 ID 查询，不校验 owner；
   - 修复版绑定当前会话用户 ID，并限制 `owner_id`；
   - 用户 A（101）读取自己的发票成功；读取用户 B（202）的发票，漏洞版返回、修复版为空。

ADV 结果：

- 模型判定：`SECOND_SQLI_VULN` vulnerable、`SECOND_SQLI_FIXED` safe、`IDOR_VULN` vulnerable、`IDOR_FIXED` safe，4/4 与真值一致；
- 本地动态对照：A 的 runtime recheck 观察到 vulnerable/fixed 的响应差异；
- D 独立复核：4/4 判定、raw、截图、会话、normalized 哈希通过；
- `poc_execution=not_run`：ADV 没有把本地运行对照写成“模型原始 POC 已执行”；
- 4 条 `reviewed`，reviewer=D。

## 6. 模型版本与证据口径

## 8. 讨论

### 8.1 为什么 Prompt 改写没有提升准确率

在本组样本上，漏洞版/修复版的差异足够明确，V0 已经能引导模型找到 source、guard、sink。V1/V2 增加的是“更严格的输出约束和验证边界”，不是新的漏洞知识，因此分类结果没有变化。

这不代表 Prompt 没有价值：

- V2 更强调普通/受控对照与“不能把 HTTP 200 当成功”；
- V2 让输出更可核查；
- 但在“是否判对”这个指标上，三个版本没有差异。

### 8.2 LLM 的优势与风险

优势：

- 快速阅读代码、总结数据流；
- 能给出行号与验证思路；
- 能生成可读的 JSON 与 POC 模板；
- 在明确样本上表现稳定。

风险：

- 注释中的指令可能改变任务（Prompt Injection）；
- 上下文不足时会过度保守或误判；
- POC 可能“看起来对但跑不起来”；
- 模型版本、会话来源、生成时设置难以逐条证明；
- 容易把“静态判断”说成“已验证”。

### 8.3 本项目的核心价值

> 不是证明“LLM 能 100% 找漏洞”，而是建立一套**可复查、可复现、可质疑**的 AI 安全审计方法。

具体包括：

1. 固定样本、Prompt、输入包和行号；
2. 保存原文、JSON、哈希、截图和 POC；
3. 用本地靶场验证，而不是只看模型自述；
4. 用交叉复核和审计规则防止“自说自话”；
5. 把模型版本和证据边界写进报告，而不是隐藏。

## 9. 结论

1. 在本组 12 个正式样本上，LLM 的漏洞判定与行号定位达到 100%，三个 Prompt 版本均无 FP/FN；
2. Prompt 从 V0 到 V2 的强化没有改变分类结果，说明“问法优化”不等于“识别能力提升”；
3. 模型能生成 POC，但原始 POC 直接可执行率不高，需要环境适配与人工复核；
4. 上下文不足会显著提高 `uncertain`，说明给模型“看多少代码”是审计设计的一部分；
5. 代码注释中的 Prompt Injection 是实际风险，防御需要在 Prompt 和流程两层处理；
6. 通过 Docker 靶场、哈希、截图、会话记录和交叉复核，项目形成了一条完整的证据链；
7. 项目完成正式 36/36、加分 26/26、测试 22/22、冻结 READY、严格审计 READY。
