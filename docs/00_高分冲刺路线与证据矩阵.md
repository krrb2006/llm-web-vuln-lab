# 高分冲刺路线与证据矩阵

## 结论与使用方法

本项目冲击高分的关键不是继续扩大概念性文字，而是让每一项课程要求都能从报告跳转到源码、Prompt、模型原文、POC、运行证据和独立复核。主实验保持 24 个成对样本、三版 Prompt 和 36 条正式记录；加分实验独立编号，不改变主实验样本和指标口径。

每次推进先运行：

```bash
python tools/check_freeze.py --report-only
python tools/audit_submission.py
python -m unittest discover -s tests -v
```

第一个命令回答“能否冻结正式实验”，第二个命令回答“课程评分项还缺什么”，第三个命令保证统计和验收工具没有被协作修改破坏。

## 必须先完成的主线

1. 合并并复核 S009 至 S024 的源码、输入包和真值证据，修复所有跨平台哈希差异。
2. 用开发集完成 V0 到 V1、V1 到 V2 的真实迭代；六份 Prompt 确认唯一文本和 SHA-256。
3. 冻结模型显示名称、样本、Prompt、环境、指标与 36 条运行计划，四人签字后才开始正式实验。
4. 每人完成 9 条记录并由指定成员复核。失败、模型拒答、无 POC 都必须保留，不能删除后缩小分母。
5. 生成统计产物并人工审阅异常项。确认主实验归档后，才执行上下文消融和其他加分实验。

## 最能拉开分差的分析

最终报告至少回答五个问题：

1. V2 相对 V0 在同一样本上纠正了多少错误，又新增了多少退化？
2. SQLi 与 XSS 的表现是否一致，差异来自判定、上下文、定位还是 POC？
3. 模型预测正确但定位错误的比例是多少，这类结果为什么不能直接进入修复流程？
4. 原始 POC、仅环境适配 POC、修改逻辑后的 POC 各有多少，真正触发漏洞的又有多少？
5. 传统工具、Prompt 注入对照和高级样例分别揭示了主实验看不到的什么边界？

所有数字必须由脚本从已复核 JSON 记录生成。对 12 个正式样本只称“本组受控样本集上的观察”，不宣称模型具有普遍准确率。

## 报告与答辩证据链

报告正文每个核心结论旁写出运行 ID，附录建立运行 ID 到证据目录的索引。答辩演示选择一条成功案例和一条失败或退化案例：成功案例展示完整调用链与 POC；失败案例展示为什么会误报、漏报或被不可信注释干扰，以及 V2 是否真正改善。

正式记录完成后，用版本化目录生成索引，避免覆盖旧版：

```bash
python tools/build_evidence_index.py --out results/final-YYYYMMDD/evidence-index.md
```

架构图应展示两条反馈边界：开发集结果可以反馈到 Prompt 迭代，正式测试结果只能进入统计与复盘，不能返回修改已冻结 Prompt。这条边界是实验可信度的重要证据。

## 禁止作为高分材料的内容

- 没有原始日志和独立复核的“成功截图”。
- 用计划数量代替已完成数量。
- 把脚本退出码 0、HTTP 200 或返回特殊字符单独当作漏洞触发。
- 只挑 V2 成功案例而不披露退化、失败和待判定。
- 把人工修正后的结论当作 LLM 原始准确率。
- 把高级样例混入主实验后重新选择更好看的指标。
