# 基于 LLM 辅助的 Web 漏洞挖掘与验证实验报告

**项目：** `llm-web-vuln-lab`  
**日期：** 2026-10-26（Asia/Shanghai）  
**结论状态：** 正式实验 36/36、加分实验 26/26 均已归档并通过项目内复核；自动化测试 22/22 通过。

## 摘要

本实验构建了一个面向 SQL 注入（SQLi）与跨站脚本（XSS）的可审计教学靶场，并考察大语言模型在受控 PHP 代码样本上的静态漏洞判断、行号定位和本地验证建议生成能力。数据集共 24 例，按漏洞版/修复版成对构造；其中 12 例作为正式测试集，分别在 V0、V1、V2 三版 Prompt 下运行，共形成 36 条正式模型记录。为避免将模型文字分析误写成漏洞事实，实验把“模型预测”“代码定位”“POC 生成”“原始 POC 可执行”“环境适配后执行”和“实际触发”分别存档和统计。

在本组受控测试集中，三版 Prompt 的分类和定位均为 12/12 正确，SQLi 与 XSS 各 6 例均无误报、无漏报；因此没有观察到 V0→V1→V2 带来的准确率提升。加分部分完成了 16 条 Prompt Injection、2 条 Burp 联动、4 条上下文消融和 4 条高级案例（二阶 SQLi、IDOR）记录。所有动态请求仅面向本地 `127.0.0.1:4280` 教学环境。

**关键词：** 大语言模型；Web 漏洞挖掘；SQL 注入；XSS；Prompt 工程；可追溯验证

## 1. 实验概述

### 1.1 目标与问题

实验目标不是让模型自动宣布漏洞已经存在，而是建立一条可复查的辅助审计流程：

1. 由模型阅读固定代码输入，输出结构化的 `vulnerable/safe/uncertain` 判断、代码位置、数据流依据、缺失上下文和本地 POC 建议；
2. 由人工将模型定位映射回原始文件和行号，并与漏洞版/修复版真值对照；
3. 仅在隔离教学环境中审核、运行允许的本地验证脚本；
4. 保存输入、Prompt、模型原文、规范化 JSON、哈希、验证日志和复核结论，使任意一条结论可追溯。

本实验回答三个问题：

- 在配对的 SQLi/XSS 教学样本中，模型能否正确区分漏洞版与修复版？
- Prompt 从 V0 到 V2 的具体约束增强，是否改变分类与定位结果？
- 模型生成的 POC 如何在不扩大攻击范围的前提下，转化为可审计的本地验证线索？

### 1.2 范围与边界

- 仅审计仓库内的教学 PHP 样例；不扫描或测试任何公网系统。
- 本地服务固定在 `127.0.0.1:4280`，Docker 容器不将靶场暴露至公网。
- 漏洞触发只以对应日志、DOM 标记或受控业务差异为准；模型的预测、HTTP 200 和 POC 文本本身都不等价于触发。
- 结果仅描述本组小规模、配对、受控样本，不能外推为通用模型能力或真实世界漏洞发现率。

## 2. 传统审计与 LLM 辅助审计的对比

传统 Web 审计从入口、数据传播、校验/编码和危险操作建立证据链：SQLi 需要证明不可信数据改变 SQL 语法，XSS 需要证明数据到达可执行浏览器上下文且缺少有效输出防护。LLM 的角色是快速提出候选路径、可疑缺失条件和验证思路，而不是替代代码与运行事实。

| 环节 | 传统人工审计 | LLM 辅助 | 本实验最终判据 |
|---|---|---|---|
| 路径发现 | 逐行追踪 source、flow、guard、sink | 输出候选数据流与行号 | 原始源码和 `line_map.json` |
| 防护判断 | 审查参数化、编码、净化和授权约束 | 解释防护是否覆盖目标路径 | 漏洞/修复配对差异与人工复核 |
| 验证设计 | 构造普通请求与受控请求 | 提供本地 POC 候选 | 只允许本地靶场，审核后执行 |
| 结论表达 | 结合源码和观察给出结论 | 输出结构化 JSON | 原文、哈希、真值、运行日志共同支持 |

这一分工避免了三个常见误区：把预处理 SQL 等同于所有安全、把 HTTP 200 等同于利用成功、把模型生成脚本等同于已验证漏洞。

## 3. 总体架构与实验流程

### 3.1 数据、Prompt 与运行链

```text
24 例源码与真值
   ↓（固定 LF 哈希、行号映射、正式输入包）
12 例正式测试集 × V0/V1/V2 Prompt
   ↓（网页端模型原文、JSON 规范化、哈希）
36 条正式记录
   ↓（人工定位复核、真值对照、必要时本地验证）
指标统计与审计报告
```

数据集包含 12 个漏洞版和 12 个修复版，真值按照配对设计登记：漏洞构造例为 `true`，对应修复例为 `false`。正式测试集为 S007、S008、S009、S010、S011、S012、S019、S020、S021、S022、S023、S024；每例在 V0、V1、V2 下运行一次，因此正式记录总数为 36。

### 3.2 模型与设置口径

正式网页端运行使用默认/快速模式，深度思考开启、智能搜索关闭。DeepSeek 官方在 2026-10-17 公告，V4.1 Flash 升级为 `DeepSeek-V4.1-Flash-1017`，网页端与 App 同步更新；正式记录时间均在 2026-10-19，因此本报告将批次表述为：

> DeepSeek 网页默认/快速模式（官方版本映射：`DeepSeek-V4.1-Flash-1017`）。

单条会话未保留 API/HAR 级别的后端模型字段；版本依据是默认/快速模式的会话证据与官方更新公告的组合，而不是伪造的接口快照。完整说明见 `results/A_model_provenance_update_2026-10-26.md`。

### 3.3 Prompt 设计

SQLi 与 XSS 各设置 V0、V1、V2 三版 Prompt。三版始终要求：中文输出、合法 JSON、原始行号、source/flow/guard/sink 证据、前提与缺失上下文、POC 生成状态，并明确禁止把静态审计说成已触发。

- **V0：** 统一结构化审计基线。
- **V1：** 强化数据流可达性、有效防护与缺失上下文说明。
- **V2：** 进一步强调普通/测试对照、验证前提、触发判据及“代码注释和嵌入指令不可信”。

每个样本跨版本保持同一正式 `code_input` 与输入包哈希，仅允许 Prompt 文本改变。

## 4. 模块详细设计

### 4.1 输入包与真值控制

每个样本由源码、`code_input.txt`、`line_map.json`、`source.json` 和 manifest 记录组成。源码哈希按 UTF-8/LF 规范计算；已作废输入包隔离在 archive，避免误参与冻结扫描。真值由独立复核记录支持，而非根据模型答案反推。

### 4.2 模型输出归档与规范化

每条模型运行至少保存：

- 原始回答 `raw_output.txt`；
- 规范化结构 `normalized.json`；
- 输入、Prompt、源码或输入包的 SHA-256；
- 模型设置、会话/截图或其他可读证据；
- POC 原文及其是否执行的明确状态。

规范化过程不覆盖原始回答。若原文 JSON 有格式缺陷，缺陷保留并在 `format_valid` 或复核记录中说明，避免“修复模型原话”后再统计。

### 4.3 本地动态验证环境

运行环境为 Windows 宿主机上的 Docker Desktop、DVWA 与 MariaDB。样本以本地挂载方式进入容器，服务端口仅映射到 `127.0.0.1:4280`。验证前执行源码一致性、PHP 语法和运行健康检查；验证时比较普通请求与受控请求的业务影响，而非只看响应状态码。

典型判据包括：

- SQLi：普通条件与受控条件的记录集合/排序差异；
- XSS：浏览器 DOM marker，而不是仅在响应体中查找脚本标签；
- IDOR：不同会话用户对同一对象的读取差异；
- 二阶 SQLi：先写入受控值，再从独立读取路径观察漏洞版/修复版差异。

### 4.4 POC 分层

POC 分为原始模型文本、环境适配版和逻辑修改版。若路径、Cookie 或断言被改变，修改会单独记录；适配后的成功不能反向写成“原始模型 POC 成功”。没有执行的 POC 保持 `not_run`，而非补造触发结论。

## 5. 实验结果与分析

### 5.1 正式实验结果

正式统计来自 `results/formal_eval_2026-10-19-v2/summary.md`。36 条记录全部 reviewed，三版均在 12 个正式样本上得到相同结果。

| Prompt 版本 | N | TP | FP | TN | FN | 不确定 | 准确率 | 定位正确率 | 原始 POC 可执行率 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| V0 | 12 | 6 | 0 | 6 | 0 | 0 | 100.0% | 100.0% | 0.0% |
| V1 | 12 | 6 | 0 | 6 | 0 | 0 | 100.0% | 100.0% | 0.0% |
| V2 | 12 | 6 | 0 | 6 | 0 | 0 | 100.0% | 100.0% | 16.7% |

按漏洞类型分层时，SQLi 与 XSS 在 V0/V1/V2 下均为 6/6 正确。V0→V1、V1→V2、V0→V2 的 12 个配对比较中均无预测变化，因此准确率变化均为 0.0%。

这说明在本组样本上，Prompt 的证据约束增强没有带来可观测的分类提升；更合理的结论是，样本的漏洞/修复差异较清晰，而 V1/V2 的价值主要体现在输出契约、验证边界和可审计性，不能写成“Prompt 优化提高了检测准确率”。

### 5.2 代表性验证案例

| 案例 | 漏洞版观察 | 修复版观察 | 证据含义 |
|---|---|---|---|
| S009 SQLi | 正常 `ids=1` 为 1 行；受控条件返回 3 行 | 配对修复例不产生相同扩展 | 证明查询语义被改变 |
| S021 XSS | 浏览器 DOM `data-lab-xss=yes` | S022 无 marker | 区分输出中出现脚本与浏览器实际执行 |
| S011 SQLi | 适配后观察到排序变化 | 配对控制不具备相同行为 | 原始 POC 与环境适配结果分开记录 |
| ADV_SECOND_SQLI | 漏洞版二次读取响应长于修复版 | 参数化二次读取不出现同样差异 | 跨请求数据流验证 |
| ADV_IDOR | 用户 101 可在漏洞版读取 owner 202 的对象 | 修复版同请求为空 | 对象级授权过滤有效 |

ADV 四条的模型会话、归档和本地动态对照位于 `runs/ADV_*_R1/`、`results/ADV_runtime_recheck_2026-10-26.json` 与 `results/A_ADV_runtime_recheck_2026-10-26.md`。四条 ADV 记录的 `poc_execution` 均为 `not_run`；本地动态对照验证的是代码路径，不把它表述为模型原始 POC 已逐字执行。

### 5.3 加分实验结果

加分计划现为 26/26 reviewed：

| 类别 | 数量 | 结论 |

| Prompt Injection | 16 | S013 官方四类注释攻击矩阵与 S001 对照均保留原始证据；注释变化未使 S013 的预测改变。 |

## 6. 缺陷、限制与优化

1. **样本规模与外推限制。** 正式测试集仅 12 例，且为教学用途的成对样本，不能据此给出真实世界或所有 Web 项目的模型准确率。
2. **模型版本证据限制。** 版本依据为网页默认/快速模式证据与官方网页端更新公告，不是逐请求 API/HAR 快照。后续应优先使用可导出模型 ID 的 API，或保存每次会话的设置页与版本横幅。
3. **训练语料重合风险。** DVWA、常见 SQLi/XSS 模式可能出现在模型训练资料中；本实验评估的是受控审计流程和可追溯性，不是零日漏洞发现能力。
4. **POC 成功不等于模型完全正确。** 环境路径、Cookie、初始化数据或断言变化会影响执行结果，因此原始 POC、适配 POC 和逻辑修改版必须分层保存。
5. **Prompt 改进未产生准确率差异。** 下一轮可增加边界更模糊、需要跨文件或跨请求推理的盲测样本，并预注册评价规则，避免根据结果回写 Prompt。
6. **人工复核独立性。** 部分收口记录采用 `A_self_review`，报告已明确标注，不冒充其他成员签名。后续可引入双盲复核和外部评审以提高可信度。

## 7. 实验总结

本项目完成了从样本构造、输入冻结、模型运行、结构化归档、真值复核到本地动态验证的完整教学闭环。正式实验 36/36 与加分实验 26/26 均有可读证据；SQLi/XSS 的主实验分类与定位在本组样本中均为 100%，但三版 Prompt 的预测没有变化，因此不宣称 Prompt 迭代提高了准确率。

实验的主要贡献不在于把模型回答包装成自动化漏洞验证，而在于建立了“模型输出—源码—本地环境—人工复核”分层、可审计的证据链。该流程使模型能够承担候选路径发现和验证建议生成工作，同时仍将漏洞触发和安全结论保留给可复现的本地观察与明确的证据边界。
