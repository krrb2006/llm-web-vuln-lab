# 网络安全大实验总执行手册

## 阅读顺序与项目目标

四位成员统一称为A、B、C、D。A负责判定规则与评估整合；B负责Prompt与模型对照；C负责样本与预处理；D负责环境与验证工程。先共同阅读本手册，再按各自操作文档执行。

最终选题为“基于LLM辅助的Web漏洞挖掘与验证——面向SQL注入和XSS的提示词迭代及误漏报分析”。采用公开靶场与注明来源的教学样本，研究同一个模型在三版Prompt下的判断、定位和POC可用性。所有结果等待实际运行，本操作包不含已完成的漏洞实验结果。

可以把本实验理解为一次有标准答案的安全审计考核：C整理题目，A确认评分依据，B设计给模型的任务说明，D准备可以检验答案的环境，四个人一起完成监考、实测与复核。标准答案必须来自代码分析和参考验证，不能取自被考核模型的回答。

## 二  技术路线和统一环境

采用Windows宿主机加WSL Ubuntu作为统一终端，Docker Desktop提供容器运行能力，浏览器访问本地DVWA；已有Linux环境也可按同样的Bash命令执行。已有可用WSL无需重装。软件版本由D记录，全组按同一环境说明操作。

仅使用一种LLM交互界面完成主要对照。若界面不能设置temperature、seed或准确模型快照，记录“界面不提供”；不要填写猜测参数。模型名称与日期发生变化时标记批次，必要时重跑该批正式对照。

执行顺序是：原始代码→标准输入包→场景Prompt→LLM报告与POC→人工运行→对照真值→分类统计→开发集优化。模块反馈只发生在开发阶段，正式测试开始后固定输入和Prompt。

全部验证使用本机靶场和教学数据，目标地址统一为http://127.0.0.1:4280。涉及XSS只观察自定义标记、提示框或页面属性变化；SQLi只观察教学数据的条件变化。运行模型代码之前由执行人阅读脚本并确认目标、文件操作和预期结果。

## 三  第一天下午就能启动的操作

### 3.1 建立工作目录

将本操作包解压到WSL的~/llm-web-lab，进入该目录。包内tools、templates、prompts目录直接保留。以下命令均为Bash，不在PowerShell中逐行混用。

```bash
cd ~/llm-web-lab
mkdir -p dataset/raw dataset/packets dataset/specs
mkdir -p runs pocs evidence results demo environment
cp templates/manifest.plan.json dataset/manifest.json
cp templates/formal_runs.plan.json runs/formal.json
python3 --version
```

只有第一次初始化时复制模板。已有实验记录后不要再次用cp覆盖。A维护dataset/manifest.json中的真值审核状态；C维护代码与来源；每人用单独分支或独立工作副本填写自己记录，再由A合并为runs/formal.json。

### 3.2 建立版本记录

```bash
git init
git status
git add docs prompts templates tools
git commit -m "docs: initialize lab workflow and templates"
```

首次提交若要求身份信息，各人设置自己的Git姓名和邮箱。不要把第三方完整仓库直接作为本项目普通文件提交；保存其来源、提交号和补丁。样本、Prompt、结果分别提交，便于回退和核查个人贡献。实时登录Cookie放在本地会话配置中，归档截图遮盖值。

### 3.3 每人的首个交付

A完成SQLi和XSS判定卡，B准备V0并阅读输出格式，C从DVWA定位一份SQLi与一份反射XSS源码，D启动靶场并完成普通请求。四人以同一例SQLi走完全过程，随后以一例XSS验证浏览器证据采集。两例通过后再扩大样本数。

## 四  样本蓝图与配额

样本编号S001到S024对模型保持中性。计划每两个样本构成同一业务的有漏洞与修复后对照。内部family_id为SQL01到SQL06、XSS01到XSS06。计划上的“有漏洞”只是构造目标；manifest中的ground_truth在双人复核通过后才填写true或false。

SQL01至SQL03和XSS01至XSS03用于开发，共12例；其余六个家族用于正式测试，共12例。代码母版、函数组织、渲染路径高度相似的变体必须归入同一家族，再整体分配到一个集合。仅改参数名不能形成新家族。若发现家族间近重复，C在冻结前重新分组并保持正负平衡。

主实验是小规模课堂对照，公开靶场可能已出现在模型训练材料中；独立测试也不等于证明未知漏洞发现能力。报告应称“在本组受控样本集上的表现”，不宣称普遍识别率。

## 五  所有成员共用的一次实验步骤

### 第一步  确认记录身份

run_id采用F_S007_V0_R1这类格式。F表示正式测试，样本、版本和重复次数共同唯一标识。开发实验使用DEV，注入对照使用INJ，重复性实验使用REP，不能混入36条主实验。

### 第二步  检查前提

核对sample_id、样本文件哈希、运行路径、环境版本和Prompt版本。浏览器普通请求成功；数据库状态符合该样本说明；存储型XSS的上一条数据已清理。D提供环境规范，案例执行人亲自完成检查。

### 第三步  发送输入

新开LLM会话，先复制该类型和版本的Prompt，再粘贴C生成的code_input.txt。不得附内部manifest、答案、low或impossible路径标签、其他版本输出。若需要后续纠正，初次输出先保存；纠正会话另编号，不替换首轮结果。

### 第四步  原样留存

保存完整输入、原始回答、模型名称、时间与界面设置截图。若输出有JSON格式错误，原文保持不动，在规范化记录里人工转录，并标明格式违约。模型没有生成POC时填poc_generated=false，不自行补一份冒充模型输出。

### 第五步  审核与执行

按D文档检查POC依赖、目标和行为。保存pocs/run_id/original.py；运行日志重定向到evidence/run_id。需要修改时另存adapted.py并保留差异，区分地址或Cookie适配与真正的验证逻辑修改。

### 第六步  观察安全影响

SQLi比较普通请求、受控真假条件及返回记录；XSS在浏览器检查标记执行。HTTP 200、出现特殊字符串或程序退出码0都不能单独证明漏洞成功。未触发、执行失败和未执行分别记录。

### 第七步  对照真值并复核

执行人填写prediction、verification、归因和证据路径；复核人检查代码、日志和判定，必要时复跑。status只有复核通过后才能从planned改为reviewed。即使模型没有报告漏洞，也必须留存该条观察并比对真实标签。

### 第八步  汇总前做完整性检查

A运行tools/evaluate.py。脚本检查正式样本、版本、重复记录、真值、复核人、证据路径和状态；它不会判断截图内容是否真的证明漏洞，内容复核仍由人完成。

## 六  进度和验收关口

|时间|A|B|C|D|共同验收|
|---|---|---|---|---|---|
|第1—2天|规则卡与标签方法|V0与会话规范|首批源码和目录|环境与普通请求|可访问靶场且输入格式统一|
|第3天|复核两例|保存首轮输出|补依赖与行号|指导两例验证|SQLi与XSS各走通一次|
|第4—5天|审核真值和口径|两轮迭代至V2|完成24例与家族划分|参考验证和复现说明|Prompt与样本可以冻结|
|第6—7天|本人9条并复核B|本人9条并复核C|本人9条并复核D|本人9条并复核A|36条正式记录完成|
|第8天|汇总归因|16条注入对照|复查来源与输入|两例Burp联动|加分证据完整|
|第9—10天|整合与评估展示|Prompt展示|预处理展示|动态复现展示|第二台电脑复现及计时彩排|

每人预计24—30小时，按实际耗时调整；这比上一版约24小时的估计增加了详细证据整理余量。复杂样本构造可能超时，第3天及时调平。先减少多模型或重复性扩展，不削掉真实验证、失败记录和两个Prompt迭代过程。

## 七  汇报和最终报告

PPT约10页：目标与架构各1页，C、B、D各2页，A的评估1页，总结与贡献1页。A开场40秒，随后C、B、D、A各约2分钟，余下时间用于结论和切换。

C演示原始代码到标准输入及行号追溯；B解释一条Prompt修改及其实际结果；D运行一个本地POC并复测修复版本；A从结果图点击或找到原始证据并解释误漏报。四个人都展示本人完成的技术文件，而非只介绍概念。

最终报告保持任务书六章：实验概述；传统与LLM技术对比；总体架构；模块详细设计；缺陷与优化；实验总结。A统一格式，每人交已经写好的小节。附录放样本索引、Prompt全文、验证日志索引、完整统计、分工与提交记录。

## 八  冻结单和完成标准

冻结单需要四人确认：样本及家族划分、真值审核、代码哈希、环境与数据库、三版Prompt哈希、模型名称、指标定义、36条运行计划。全部确认后开始正式测试。

最终完成标准是：随机抽一条结论，能找到代码、Prompt、模型原文、POC或未生成说明、观测证据、审核人与统计位置；另一成员能复现代表案例。真实结果无提升时如实写“未观察到稳定提升”，仍可通过完整设计和归因体现实验价值。
