# 漏洞判定卡（SQLi / XSS 审核标准）

> 用途：A 维护的组内判定标准。用于真值审核与对模型结论的人工复核。
> 本文件仅组内使用，**不发送给被评估的 LLM**。
> 原则：先定规则、再看结果；每条结论只允许「满足 / 不满足 / 未知」三种取值，
> 且必须附上「源码文件与原始行号 + 运行证据」；证据不足一律写「未知」，不得凭经验假定。

## 0 通用要求

1. **结论三值**：满足、不满足、未知。禁止出现「应该是」「基本是」等模糊措辞。
2. **必须三项证据**：
   - 源码位置：`文件相对路径:起始行号`（用原始文件行号，不用输入包里的 F01 别名）。
   - 调用链：入口 → 中间处理 → 危险操作/输出位置，逐段写明。
   - 运行证据：普通请求、受控异常请求、响应/浏览器/数据库现象，或「未验证」。
3. **引用不存在的行号 = 判定无效**：审核前先用 `nl -ba` 核对真实行号；运行文件与
   本地源码哈希不一致时（见 D 手册），不得据本地行号解释运行现象。
4. **一次 POC 失败不能支撑「安全」标签**；同样，一次脚本报错也不能单独证明「有漏洞」。
5. **争议必须按第 6 节流程处理**，先解决原因再确认标签，不允许「少数服从多数」直接定案。

## 1 SQL 注入 —— 四项必要检查

四项**全部满足**才判「有漏洞」。任何一项不满足即判「不满足（该样本边界内不构成 SQLi）」；
无法确认某一项时该项记「未知」，整条结论为「待判定」。

### 检查 1：输入来源是否受外部控制

- 判据：值是否来自请求参数、Cookie、Session、HTTP 头、上传内容，或数据库中已受外部影响
  的数据。必须写出**变量从哪个入口取得**，例如 `$_GET['name']`，不能只写「这里有输入」。
- 满足 = 明确写出入口与变量名；不满足 = 该值是常量/内部生成且不可被外部影响；未知 = 入口不明确。

### 检查 2：该值是否影响 SQL 语法结构

- 判据：值是否进入**语句结构**（拼接字符串、动态列名/表名/排序方向、`$where` 片段等）。
- 关键区分：仅作为预编译语句的**绑定值**进入查询，不视为语法结构注入；
  动态列名/排序方向不能简单用值占位符，需单独看白名单映射。
- 满足 = 值通过拼接进入 SQL 语句并参与语法；不满足 = 仅作绑定值；未知 = 无法确认进入方式。

### 检查 3：该 SQL 是否在真实路由中可达并被执行

- 判据：这条 SQL 位于实际会执行的入口路径上，不是死代码、未调用函数、其它数据库分支、
  被 `if(false)` 包裹的代码或仅定义未调用的辅助函数。
- 满足 = 入口可达且该语句被触发；不满足 = 不可达/不执行；未知 = 调用链断裂，无法确认执行。

### 检查 4：现有校验是否真正约束危险位置

- 判据：整数白名单、绑定参数、字符串转义各自**作用范围**是否覆盖危险点。不得把 HTML 编码
  当作 SQL 防护；不得看到 `prepare` 就忽略其**之前**已经拼入的不可信 SQL 结构。
- 满足 = 没有任何有效约束；不满足 = 危险位置被适用的防护覆盖；未知 = 防护存在但作用范围无法确认。

### 判定结论模板

> 在 `S00X/index.php:NN`，请求参数 `name`（`$_GET['name']`）经 `...` 拼入 SQL 语句，
> 于 `:MM` 行执行；未观察到绑定或等效约束，参考测试中真假条件导致返回结果出现预期差异，
> 故在本记录环境下标为「有漏洞」。—— 行号与现象必须替换为真实证据。

安全样本示例（要求同样给出证据）：

> 所检查目标路径中，`name` 作为绑定值进入固定查询（`prepare` + `bind_param`），
> 普通业务与异常输入回归符合预期，故标为「安全」。

## 2 XSS —— 五项检查

五项**全部满足**才判「有漏洞」。输出上下文必须明确区分：HTML 正文、带引号属性、
URL 属性、JavaScript、DOM 插入。同一 HTML 编码不能直接当作 URL 协议校验或 JS 上下文防护。

1. **输入来源**：值从请求/Cookie/存储数据等外部可控位置取得，写出入口。
2. **存储或传递路径**：反射型看参数直达输出；存储型必须**同时**看写入与读取渲染两条路径。
   写入用参数化不等价于「读出后拼进 HTML 就安全」。
3. **最终输出位置**：确定落入哪个上下文（正文/属性/URL/JS/DOM），并写出对应行号。
4. **上下文适配的编码或净化**：编码/净化是否与上下文匹配。
5. **浏览器执行可能性**：是否可在浏览器执行用户可控脚本（用 `document.documentElement.dataset.labXss='yes'`
   这类不读 Cookie、不外发的标记验证）。自动加载不执行不能直接标安全；普通文本出现不等于脚本执行。

存储型样本要求：写入成功 ≠ XSS 成功，必须确认「写入 → 另一请求读出 → 渲染 → 执行」全链。

## 3 风险分级（课堂说明用，不等同 CVSS）

- **高**：样本边界内可稳定改变查询语义或执行用户可控脚本，并影响目标业务。
- **中**：需额外状态或用户交互，但前提可复现。
- **低/待定**：主要证据不足、影响不明或缺少关键上下文。
- 严重性与证据充分性**分列**记录，不能把「未知证据」简单归为低风险。

## 4 与统计口径的衔接

判定卡只回答「这个样本在记录环境下是不是漏洞」；模型预测归类见 `docs/metrics_protocol.md`。
判定卡结论（true/false）在双人复核通过后写入 `dataset/manifest.json` 的 `ground_truth`；
复核通过前保持 `null`，`status` 保持 `planned`。

## 5 证据留存要求

- 普通请求、异常请求、响应/浏览器状态、关键源码截图、文件哈希（`case_code_sha256`）。
- 参考验证单独标记 `reference`，不得冒充被评估模型生成的 POC。
- 证据路径用**相对项目根目录**的真实文件（如 `evidence/truth/S001/review.md`）。

## 6 争议处理规则

1. 争议先归类为四种原因之一：代码上下文不足 / 运行与源码不一致 / 参考验证不充分 / 目标范围不一致。
2. 按原因补齐：缺上下文找 C 补依赖与调用者；不一致先核对哈希（D 手册）；参考验证不足补做受控对照；
   范围不一致重新明确评估边界。
3. 每类争议在 `truth_review.md` 卡片的「争议与解决记录」中记录**提出人、原因归类、补充证据、最终结论**。
4. 仍无法达成一致时，该样本 `ground_truth` 保持 `null`，`status` 记 `disputed`，**不得**凭投票或
   随意取值进入统计；最终解决后由 A 统一更正并全版本一致重算。
