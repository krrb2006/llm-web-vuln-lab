## 一  第一天建立判定卡

复制templates/truth_review.md，为样本S001—S008各建一份内部记录。每张卡回答下列问题，结论只使用“满足、不满足、未知”，并列出文件和原始行号。

### 1.1 SQL注入的四项必要检查

第一，输入是否由请求、Cookie或数据库中已受外部影响的内容控制。指出变量从哪里取得，不能只写“这里有输入”。

第二，该值是否影响SQL语法结构。字符串拼接应逐段核对；如果它只作为预编译语句的绑定值，一般不能按普通字符串注入处理。动态列名、排序方向等不能简单使用值占位符，需要单独审核白名单映射。

第三，这条SQL是否在实际路由中可达并被执行。死代码、未调用函数、另一数据库分支不能直接计入该样本的可触发漏洞。

第四，当前校验是否真正约束危险位置。整数白名单、绑定参数、字符串转义的作用范围不同；不得把HTML编码当作SQL防护，也不得看到prepare就忽略它之前已经拼入的不可信SQL结构。

### 1.2 XSS的五项检查

检查输入来源、存储或传递路径、最终输出位置、上下文适配的编码或净化、浏览器执行可能性。输出上下文至少区分HTML正文、带引号属性、URL属性、JavaScript和DOM插入。

HTML正文与带引号普通属性可采用适当HTML编码，但同一编码不能直接当作URL协议校验或JavaScript上下文防护。存储型样本必须同时看写入和读取渲染路径；写入数据库使用参数化并不代表读出后拼进HTML就安全。

### 1.3 判定结论示例

“在F01第18行，请求参数q经过F02第7行直接拼入查询，F02第9行执行；未观察到绑定或等效约束。参考测试中真假条件导致返回结果出现预期差异，故在记录环境下标为有漏洞。”这是一种写法示例，行号与现象必须替换为真实证据。

安全样本应写“所检查目标路径中，输入作为绑定值进入固定查询；普通业务与异常输入回归符合预期”。一次POC失败不能独自支撑安全标签，需同时分析防护覆盖范围。

## 二  真值审核的实际步骤

步骤1：打开C提供的sample_card和原始源码，检查入口、依赖、输出位置与配对关系。若仅给一个函数但调用者有关键过滤，要求C补齐。

步骤2：按D的环境说明部署该样本，先验证普通业务可用，再运行参考验证。参考验证用于建立答案，单独标记reference；不得冒充被评估模型生成的POC。

步骤3：保存普通请求、异常请求、响应或浏览器状态、关键源码截图以及文件哈希。若是修复样本，普通业务也必须正常，不能通过破坏功能制造“安全”。

步骤4：请C复核A标注的8例；A复核D标注的8例。争议分为代码上下文不足、运行与源码不一致、参考验证不充分、目标范围不一致，先解决原因再确认标签。

步骤5：在dataset/manifest.json写入ground_truth、truth_reviewer、truth_evidence，状态改为ready。expected_design仅是构造目标，不进入真实评分。

```json
{
  "sample_id": "S001",
  "ground_truth": null,
  "truth_reviewer": "",
  "truth_evidence": [],
  "status": "planned"
}
```

null必须由审核后的true或false替换；证据路径使用相对项目根目录的真实文件，例如evidence/truth/S001/review.md。不要把这段内部记录发送给LLM。

## 三  写出三级分析机制

|层级|人工与LLM要检查什么|可保存的证据|
|---|---|---|
|代码语法与依赖|语言、变量来源、函数定义、控制流、模板和库版本|相关源码与缺失依赖清单|
|漏洞语义|输入到查询或输出的路径；沿途安全处理是否适用|来源至危险操作的代码引用|
|业务影响|触发前提、可影响的教学数据、所需登录状态和作用范围|参考请求、响应与浏览器现象|

报告描述的是可执行的审计流程与模型输出证据，不推断LLM内部真实思维。对模型给出的“我仔细推理后认为”，仍需逐条检查代码证据。

### 风险分级的简明规则

高：在当前样本边界内能够稳定改变查询语义或执行用户可控脚本，并影响目标业务；中：需要明确额外状态或用户交互，但前提可复现；低或待定：主要证据不足、影响不明或缺少关键上下文。严重性和证据充分性分列，不能把未知证据简单归为低风险。此分级用于课堂说明，不等同CVSS。

## 四  正式实验记录怎样分类

prediction只接受vulnerable、safe、uncertain。前两者分别表示模型报告目标漏洞和未报告目标漏洞；uncertain表示模型明确需要补充信息。只有明确预测和真实标签的组合才能进入TP、FP、TN、FN。

|真实标签|模型vulnerable|模型safe|模型uncertain|
|---|---|---|---|
|有漏洞|TP|FN|U_positive|
|安全对照|FP|TN|U_negative|

精确率为TP除以TP加FP；保守召回率为TP除以全部实际阳性数，分母包括U_positive；误报率为FP除以全部实际阴性数。全样本判对比例为TP加TN除以所有样本数，uncertain保留在分母，另报待判定率。

没有阳性报告时精确率为N/A。模型回答缺失、API或界面故障不是safe，先保留运行失败状态，按预定规则重试并另编号；若无法补全，最终标明实验不完整，不能静默缩小样本数。

### 定位正确与预测正确分开

模型恰好猜中一个阳性样本，但引用了无关行号，检测标签上可能计TP，定位与证据质量仍不合格。在复核表写location_correct=false并解释。不能只用二分类准确率来证明模型审计能力全面可靠。

### POC统计的阶段区别

raw_execution_ok表示原始代码未修改、仅按说明配置环境后正常执行；environment_execution_ok表示只改目标、会话、路径等环境参数后正常执行；logic_changed表示人工改过payload逻辑、请求流程或成功断言。执行成功和verification=triggered分开。

后续曾改逻辑，不会抹去之前某个阶段真实发生的执行结果；各阶段结果需要对应日志。仅在修改逻辑后成功的脚本不得计入原始或仅环境适配后的可执行率。

## 五  使用评价辅助脚本

先检查tools/evaluate.py中的口径是否与本组冻结单一致。脚本只读取JSON和证据路径，不联网、不调用LLM、不执行POC。所有证据路径以项目根目录为基准。

```bash
cd ~/llm-web-lab
python3 tools/evaluate.py \
  --manifest dataset/manifest.json \
  --runs runs/formal.json \
  --root . \
  --out results/final_v1
```

输出summary.json与summary.md。已经存在同名输出时脚本拒绝覆盖，修订后另用final_v2等目录。开发阶段需要查看进度时可添加--allow-partial，此时输出明确标为临时结果；若真值尚未审核，脚本仍会拒绝评分。

|报错|解释与处理|
|---|---|
|unreviewed ground truth|真值仍为null，先完成代码和参考验证审核|
|missing evidence|记录指向不存在文件，补齐文件或修正相对路径|
|duplicate formal run|同一样本同版本重复计数，将重复实验放到repeat阶段|
|run not reviewed|执行人或复核人尚未完成该条，不能算最终结果|
|operator mismatch|执行人和冻结任务计划不一致，先记录正式交接并同步计划|

脚本输出之后人工抽查每版至少2例，手算统计并核对；尤其检查uncertain、空POC和逻辑修改案例。辅助脚本检查过的测试输入是合成软件测试数据，与课程实验结果没有关系。

## 六  误漏报归因与降噪

每例错误填写“现象—证据—主要原因—修正措施—是否复测”。主要原因从缺上下文、判定规则不适配、模型编造位置、会话或环境错误、POC逻辑错误、浏览器状态干扰、真值争议中选一项，必要时增加次要原因。

示例：模型见到SQL拼接就报警，但该值在唯一可达路径中被转换为受约束整数。检查处理语句、异常输入和实际查询后再决定是否误报。另一个例子是模型看到htmlspecialchars就判安全，却忽略该数据进入URL协议位置；需要按对应上下文检查。

过滤规则必须写具体条件。例如“仅在固定SQL模板、所有目标值已绑定且没有拼入其他不可信语法时，过滤值注入报警”；不能写成“出现prepare就忽略”。漏报核查应遍历入口、辅助函数、模板和存储后读取路径。

V2的预测差异用于衡量Prompt方案；人工复筛后的结果另报最终确认数和保留率，不能把人工修正后的全对结果当作LLM本身准确率。发现正式测试真值错误时冻结原记录，修订版本并对所有Prompt一致重算，写入更正说明。
