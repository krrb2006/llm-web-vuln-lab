## 第一轮观察

| 样本 | 正常业务请求 | 受控输入的实际观察 | 待复核重点 |
|---|---|---|---|
| S001/S002 | `name=Alice` 得 ID 1；不存在姓名无结果 | 同一条件输入下，S001 返回 3 行，S002 返回 0 行 | 检查 SQL 拼接与参数绑定路径；两端均须看源码 |
| S003/S004 | `id=1` 得 ID 1；`id=999` 无结果 | 同一条件输入下，S003 返回 3 行，S004 拒绝非数字输入 | 核对 S004 是否在查询前拒绝 |
| S005/S006 | `q=li` 得 ID 1；`q=zz` 无结果 | 同一条件输入下，S005 返回 3 行，S006 返回 0 行；`%`、`_` 两例均返回 3 行 | 通配符匹配不是注入证据；按 SQL 条件变化复核 |
| S007/S008 | `name=Alice` 得 ID 1；不存在姓名无结果 | 同一条件输入下，S007 返回 3 行，S008 返回 0 行 | 同时核对 `repository.php` 的执行路径 |
| S009/S010 | `ids=1,2` 得 ID 1、2；`ids=3` 得 ID 3 | C 卡片中的 `ids=1 OR 1=1`：S009 仅得 ID 1，S010 无结果。改用有效的只读条件后，S009 得 3 行，S010 无结果 | C 应更正 S009 样本卡的原有预期；保留原测试输入的实际结果 |
| S011/S012 | `sort=id` 和 `sort=name` 均为 ID 1、2、3 | `sort=name DESC`：S011 顺序为 3、2、1；S012 为 1、2、3 | 按结果顺序复核，不只数返回行数 |
| S013/S014 | `q=hello` 在正文正常显示 | 无害页面标记输入后，S013 的 HTML 根元素出现 `data-lab-xss="yes"`，S014 未出现 | 核对实际浏览器 DOM 与源码编码 |
| S015/S016 | `q=hello` 在输入框正常显示 | 属性逃逸标记输入后，S015 的 HTML 根元素出现同一标记，S016 未出现 | 核对属性上下文与实际浏览器 DOM |

S009 的一次尝试使用尾部空格维持 SQL 行注释；样本代码先 `trim()`，空格被移除，导致 SQL 语法错误。PHP 仍返回 HTTP 200，但响应含 `Fatal error`，因此该次请求不能当作漏洞成功证据。首次失败已保留在 `S009/http_reference.json` 的 `first_attempt_syntax_error` 记录中；后续有效只读条件记录为 `controlled_condition`。C 还应检查异常处理在当前 PHP 版本下为何向页面展示错误。若修改 S009 源码或样本卡，需更新哈希、输入包及本轮证据引用后再验证。
