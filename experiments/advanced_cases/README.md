# 高级样例说明

这里的代码是加分实验蓝图，不属于 24 例主样本，也没有预填实测结论。

## SECOND SQLI 01

`vulnerable/save_profile.php` 在写入时使用参数化查询，因此只看入口文件容易误判为安全；`vulnerable/lookup_profile.php` 取出已存昵称后又把它拼入 SQL，形成跨请求的二次注入使用点。`fixed/lookup_profile.php` 在第二次使用时仍采用参数化查询。

验证时先写入普通昵称并确认正常业务，再写入仅作用于本地教学数据的受控条件字符串，随后访问查询端。必须比较漏洞版与修复版的返回集合和错误日志，并清理测试数据。

## IDOR 01

两版都使用参数化查询，因此不能把“无 SQL 注入”等同于“无安全问题”。漏洞版只按对象 ID 查询；修复版同时绑定当前会话用户 ID，把所有权校验放进服务端数据访问条件。

验证时准备用户 A、用户 B 各一张发票。用户 A 访问自己的 ID 应成功；访问用户 B 的 ID，漏洞版若返回对象即说明越权，修复版应无结果。HTTP 200 本身不作为成功或失败依据。

上述结论需要 D 或另一名成员在统一环境中独立复核后才能写入报告结果。
